# فرایند انتشار نسخه

نسخه‌های MeshSync مایل‌استون‌های واقعی پروژه‌اند، نه عدد بازی. هر نسخه
یک لایهٔ کامل و قابل تست از سیستم را اضافه می‌کند. نمودار:
[docs/assets/release-pipeline.svg](../assets/release-pipeline.svg).

## نقشهٔ نسخه‌ها

| نسخه | محتوا |
|---|---|
| `0.1.0` | هستهٔ ایجنت: موتور هش C++20، ایجنت Go (هویت، کشف UDP، جفت‌سازی و اعتماد، پوشه‌های اشتراکی، نمایهٔ فایل، برنامه‌ریز sync، انتقال قطعه‌ای ازسرگیری‌پذیر، تأیید صحت، تعارض‌ها، کنترل پهنای باند، وضعیت SQLite، API نسخه‌دار + رویدادهای WS، fallback هش Go) + تست‌های e2e |
| `0.2.0` | کنسول وب: کنسول ۹-فضایی React/TS، WS بلادرنگ، فارسی/انگلیسی + RTL، تم تیره، رجیستری ایجنت با Prisma |
| `0.3.0` | کلاینت Flutter: هدف Android و Linux، ۷ صفحه، کلاینت تایپ‌شدهٔ API، polling زنده، فارسی/انگلیسی |
| `0.4.0` | عملیات: مستندات دوزبانه، workflowهای CI/CD، بسته‌بندی Docker، ابزار انتشار، SBOM |
| `1.0.0` | پایدار: اعتبارسنجی نهایی، اسکرین‌شات‌های واقعی، آرتیفکت‌های انتشار (باینری، checksum، SBOM) |

فهرست کامل تغییرات: [CHANGELOG.md](../../CHANGELOG.md).

## خط تولید انتشار

هر تگ `vX.Y.Z` از همین شش مرحله رد می‌شود:

۱. **tag** — ثبت تگ `vX.Y.Z` (بعد از ثبت مطلب نسخه در CHANGELOG).
۲. **validate** — ماتریس اعتبارسنجی per-componnet:

   | کامپوننت | دستور |
   |---|---|
   | ایجنت Go | `go vet` · `go build ./…` · `go test ./…` (شامل e2e دو‌ایجنتی) |
   | موتور C++ | `make` · `make test` |
   | کنسول وب | `bun run lint` · build تولیدی |
   | Flutter | `flutter analyze` · `flutter test` |

   هر گیت قرمز، کل خط تولید را می‌ایستاند؛ نسخه‌ای با تست fail شده
   منتشر نمی‌شود.
۳. **package** — آرشیوهای `meshsync-agent` (کامپایل متقاطع برای
   پلتفرم‌های پشتیبانی‌شده)، موتور `meshsync-native` جایی که toolchain
   واقعی هست (linux/amd64 با g++ و darwin با clang++؛ آرشیوهای
   linux/arm64 و windows فقط ایجنت‌اند — این محدودیتِ صادقانه در
   workflow ثبت شده)، و image داکر (رجیستری کانتینر) که فقط ایجنتِ Go خالص را
   دارد؛ worker عمداً باندل نمی‌شود و ایجنت در کانتینر به هش Go
   برمی‌گردد.
۴. **checksum** — فایل `SHA256SUMS` روی همهٔ آرتیفکت‌ها.
۵. **SBOM** — فهرست اجزای نرم‌افزاری نسخه به قالب CycloneDX.
۶. **release** — انتشار نسخه با آرتیفکت‌ها و یادداشت‌های نسخه.

## قواعد نسخه‌گذاری

- SemVer: در `0.x` ممکن است رفتارها تغییر کند (فاز توسعه)؛ بعد از
  `1.0.0`، تغییر رفتار فقط با major جدید.
- شمارهٔ نسخهٔ ایجنت در `agent/internal/version/version.go` ثابت شده و
  `--version` و `GET /health` همان را برمی‌گردانند.
- افزودن endpoint یا فیلدِ اختیاری به API نسخهٔ ۱ = نسخهٔ patch/minor؛
  شکستن سازگاری = نسخهٔ major و یک قرارداد `v2` جدید.
- HELLO ریموت شامل رشتهٔ نسخه است؛ تغییر پروتکل سیمی باید طوری طراحی شود
  که نسخه‌های مجاور بتوانند handshake را به‌آرامی رد کنند.
