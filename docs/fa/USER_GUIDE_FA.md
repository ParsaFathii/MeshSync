# راهنمای کاربر

این سند جریان روزمرهٔ کار با MeshSync را از دید کاربر می‌گوید. همهٔ
مثال‌ها با curl نوشته شده‌اند؛ کنسول وب و کلاینت Flutter دقیقاً همین
فراخوانی‌ها را انجام می‌دهند. فرض: ایجنت روی `127.0.0.1:3040` گوش
می‌دهد (دستگاه دوم روی `3041`).

## سلامت سیستم و وضعیت دستگاه

```sh
curl -s http://127.0.0.1:3040/api/v1/health
curl -s http://127.0.0.1:3040/api/v1/device
```

خروجی `device` شامل شناسهٔ همتا، اثر انگشت کلید، نسخه، وضعیت موتور هش
(`cpp-worker-1.0.0` یا `go-fallback`) و آمار لحظه‌ای است: تعداد پوشه‌ها،
فایل‌های نمایه‌شده، همتاهای مورد اعتماد/آنلاین، انتقال‌های فعال و
کامل‌شده، تعارض‌های باز و آخرین همگام‌سازی.

## کشف همتاها

کشف به‌صورت خودکار در پس‌زمینه انجام می‌شود: هر ایجنت هر ۵ ثانیه یک
بیکِن JSON به گروه مالتی‌کست `239.255.42.42:4100` می‌فرستد و بیکِن‌های
دیگران را می‌شنود. برای یک جاروی دستی:

```sh
curl -s -X POST http://127.0.0.1:3041/api/v1/discovery/scan
```

همتاهای تازه با رویداد `PEER_DISCOVERED` ثبت می‌شوند و در وضعیت
`DISCOVERED` می‌مانند. کشف هیچ‌وقت اعتماد ایجاد نمی‌کند؛ این طراحی
عمدی است.

## جفت‌سازی و اعتماد

از دستگاه A به B درخواست جفت‌سازی بفرستید (پورت peer مربوط به B):

```sh
curl -s -X POST http://127.0.0.1:3040/api/v1/peers/pair \
  -H 'Content-Type: application/json' -d '{"address":"192.168.1.20:4041"}'
```

ایجنت A در همین اتصال اول، کلید عمومی Ed25519 دستگاه B را از گواهی
TLS آن یاد می‌گیرد. سمت B، درخواست به‌صورت یک همتای `PAIRING` با رویداد
`PAIR_REQUESTED` دیده می‌شود و باید صریحاً تأیید شود:

```sh
# روی B — peerId مربوط به A را از GET /api/v1/peers بردارید
curl -s -X POST http://127.0.0.1:3041/api/v1/peers/<A-PEER-ID>/approve
```

بعد از تأیید، B فریم `PAIR_APPROVED` به A می‌فرستد و رکورد A هم به
`TRUSTED` تغییر می‌کند. اگر هر دو طرف از قبل همدیگر را تأیید کرده
بودند، بلافاصله دو طرف `TRUSTED` می‌شوند.

لغو اعتماد و حذف رکورد:

```sh
curl -s -X POST http://127.0.0.1:3040/api/v1/peers/<B-PEER-ID>/revoke
curl -s -X DELETE http://127.0.0.1:3040/api/v1/peers/<B-PEER-ID>
```

همتای لغو‌شده (`REVOKED`) در Handshake رد می‌شود و درخواست جفت‌سازی
جدیدش تا زمانی که رکوردش حذف نشده، reject می‌شود. جزئیات بیشتر در
[PEERS_FA.md](PEERS_FA.md).

## پوشه‌های اشتراکی

همگام‌سازی بین دو همتای مورد اعتماد وقتی شروع می‌شود که **هر دو طرف
پوشه‌ای با یک نام** تعریف کرده باشند (مسیرها می‌توانند متفاوت باشند):

```sh
# روی A
curl -s -X POST http://127.0.0.1:3040/api/v1/shared-folders \
  -H 'Content-Type: application/json' \
  -d '{"name":"Documents","path":"/home/you/shared-a"}'

# روی B — همان نام، مسیر متفاوت
curl -s -X POST http://127.0.0.1:3041/api/v1/shared-folders \
  -H 'Content-Type: application/json' \
  -d '{"name":"Documents","path":"/home/you/shared-b"}'
```

مسیر باید دایرکتوری موجودِ مطلق باشد و نام تکراری نباشد. بعد از افزودن،
ایجنت پوشه را کامل نمایه‌ می‌کند و با fsnotify زیر نظر می‌گیرد؛ فایل‌هایی
که بیرون از MeshSync تغییر کنند، بلافاصله دوباره نمایه می‌شوند.

اسکن مجدد و حذف پوشه:

```sh
curl -s -X POST http://127.0.0.1:3040/api/v1/shared-folders/1/rescan
curl -s -X DELETE http://127.0.0.1:3040/api/v1/shared-folders/1
```

اسکن، هر فایل را با هش جاری مقایسه می‌کند، فایل‌های غایب را tombstone
می‌کند و خروجی `scanned/changed/removed/durationMs` می‌دهد. حذف پوشه فقط
ردیابی را متوقف می‌کند؛ فایل‌ها روی دیسک می‌مانند.

## کار با فایل‌ها

```sh
# فهرست محتوای یک دایرکتوری (ترکیب دیسک + نمایه)
curl -s "http://127.0.0.1:3040/api/v1/files?folder=1&path="

# جزئیات یک فایل به‌همراه نگاشت قطعه‌ها و نسخه‌های همتاها
curl -s "http://127.0.0.1:3040/api/v1/files/detail?folder=1&path=notes.txt"

# دانلود محتوا
curl -sOJ "http://127.0.0.1:3040/api/v1/files/content?folder=1&path=notes.txt"

# ساخت/جایگزینی فایل (متن)
curl -s -X POST http://127.0.0.1:3040/api/v1/files \
  -H 'Content-Type: application/json' \
  -d '{"folder":1,"path":"todo.txt","content":"سلام","encoding":"utf8"}'

# ساخت/جایگزینی فایل (باینری، multipart)
curl -s -X POST http://127.0.0.1:3040/api/v1/files \
  -F folder=1 -F path=photo.jpg -F file=@photo.jpg

# حذف — به سطل زبالهٔ ایجنت می‌رود و tombstone می‌شود
curl -s -X DELETE "http://127.0.0.1:3040/api/v1/files?folder=1&path=todo.txt"
```

در فهرست، دایرکتوری‌ها اول می‌آیند و مرتب‌سازی case-insensitive است.
فیلد `remotePeers` نشان می‌دهد کدام همتاهای مورد اعتماد نسخهٔ به‌روزی
از همان فایل را دارند.

## همگام‌سازی

همیشه می‌توانید قبل از اجرا، برنامه را ببینید (هیچ فایلی لمس نمی‌شود):

```sh
B=$(...)   # peerId دستگاه B
curl -s "http://127.0.0.1:3040/api/v1/sync/plan?peer=$B&folder=1"
```

خروجی شامل `summary` (تعداد pull/push/delete/conflict/unchanged) و
اقدام per-path با هش محلی، هش ریموت و آخرین هش همگام‌شده است. اجرا:

```sh
curl -s -X POST http://127.0.0.1:3040/api/v1/sync/run \
  -H 'Content-Type: application/json' -d "{\"peer\":\"$B\",\"folder\":1}"
```

پاسخ شامل `sessionId` و همان برنامه است. اجرا در پس‌زمینه انجام
می‌شود و پیشرفت را از انتقال‌ها و رویدادها دنبال کنید:

```sh
curl -s "http://127.0.0.1:3040/api/v1/transfers?status=TRANSFERRING"
curl -s "http://127.0.0.1:3040/api/v1/sync/sessions"
curl -s "http://127.0.0.1:3040/api/v1/events?limit=50"
```

اگر تنظیم `autoSyncSeconds` را مثلاً ۶۰ بگذارید، ایجنت به‌طور دوره‌ای
هر پوشهٔ مشترک با هر همتای آنلاینِ مورد اعتماد را همگام می‌کند.

## مدیریت انتقال‌ها

```sh
curl -s -X POST http://127.0.0.1:3040/api/v1/transfers/<ID>/pause
curl -s -X POST http://127.0.0.1:3040/api/v1/transfers/<ID>/resume
curl -s -X POST http://127.0.0.1:3040/api/v1/transfers/<ID>/cancel
curl -s -X POST http://127.0.0.1:3040/api/v1/transfers/<ID>/retry
```

- `pause` issuing قطعه‌های جدید را متوقف و وضعیت را ذخیره می‌کند؛ حتی
  بعد از ری‌استارت ایجنت می‌ماند (در بوت، انتقال‌های ناتمام به `PAUSED`
  منتقل می‌شوند).
- `resume` از اولین قطعهٔ pending ادامه می‌دهد.
- `retry` یک انتقال `FAILED` را با همان نگاشت قطعه‌ها دوباره صف می‌کند.

متریک‌های زنده — درصد، سرعت (پنجرهٔ ۴ ثانیه)، ETA و تعداد قطعه‌های
انجام‌شده — از وضعیت واقعی انتقال می‌آیند؛ هیچ چیز شبیه‌سازی نیست.

## تعارض‌ها

وقتی هر دو دستگاه یک فایل را از آخرین نسخهٔ مشترک تغییر داده باشند،
برنامه‌ریز به‌جای بازنویسی، تعارض ثبت می‌کند و مسیر را از اجرا حذف
می‌کند:

```sh
curl -s http://127.0.0.1:3040/api/v1/conflicts

curl -s -X POST http://127.0.0.1:3040/api/v1/conflicts/4/resolve \
  -H 'Content-Type: application/json' -d '{"action":"KEEP_BOTH"}'
```

چهار اقدام: `KEEP_LOCAL`، `KEEP_REMOTE`، `KEEP_BOTH` (نسخهٔ ریموت با نام
`report (conflict from mesh-beta 2026-10-08).pdf` کنار فایل محلی می‌نشیند
و نسخهٔ محلی روی مسیر اصلی برنده می‌شود) و `LATER` (تعارض باز می‌ماند،
هیچ داده‌ای لمس نمی‌شود). در هر حالتی نسخهٔ بازنده ابتدا به سطل زباله
می‌رود. توضیح کامل در [CONFLICTS_FA.md](CONFLICTS_FA.md).

## رویدادها و WebSocket

```sh
# دریافت رویدادهای جدید از یک شناسهٔ مشخص (قدیمی→جدید)
curl -s "http://127.0.0.1:3040/api/v1/events?sinceEventId=512&limit=100"
```

WebSocket روی `GET /api/v1/events/ws`: فریم‌های `hello` (اسنپ‌شات
دستگاه)، `event`، `transfer` (پیشرفت، حدود ۸ فریم بر ثانیه به ازای هر
انتقال)، `peers`، `device` و `pong`. کلاینت `{"kind":"ping"}` می‌فرستد.
قطع‌شدن اتصال طبیعی است؛ کلاینت‌ها با backoff دوباره وصل می‌شوند و
وضعیت را از REST می‌گیرند — وضعیت کهنهٔ WS هرگز مرجع نیست.

## کنسول وب

`bun run dev` و باز کردن <http://localhost:3000>. ۹ فضای کاری دارد:
داشبورد، پوشه‌ها، فایل‌ها، همتاها، همگام‌سازی، انتقال‌ها، تعارض‌ها،
فعالیت و تنظیمات. زبان فارسی/انگلیسی (با RTL خودکار)، تم تیره و
ثبت endpoint ایجنت‌ها از بخش همتاها/تنظیمات در دسترس است. همهٔ
به‌روزرسانی‌ها همان WebSocket بالا را مصرف می‌کنند.

## کلاینت Flutter

برای اندروید و لینوکس: ۷ صفحه (دستگاه، پوشه‌ها/فایل‌ها، همتاها،
همگام‌سازی، انتقال‌ها، تعارض‌ها، تنظیمات)، کلاینت تایپ‌شدهٔ API و
polling زندهٔ پیشرفت، با دو زبان فارسی و انگلیسی.
