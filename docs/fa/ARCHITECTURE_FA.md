# معماری MeshSync

نمای لایه‌ای: کلاینت‌ها (Flutter، کنسول وب، curl) فقط با API محلیِ
HTTP/WebSocket ایجنت خودشان حرف می‌زنند؛ ایجنت Go مالک همهٔ وضعیت است
(SQLite + فایل‌سیستم)، کار همگام‌سازی را با یک موتور هش بومیِ اختیاری
(C++) انجام می‌دهد و با همتاها روی TLS 1.3 صحبت می‌کند. هیچ کامپوننت
سروری و هیچ سرویس ابری وجود ندارد.

نمودار: [docs/assets/architecture.svg](../assets/architecture.svg).

```
کلاینت‌ها (Flutter / کنسول وب / curl)
        │ HTTP + WebSocket — 127.0.0.1:3040
        ▼
meshsync-agent (Go)
  api/       REST نسخهٔ ۱ + رویدادهای WS، توکن، rate limit
  app/       سیم‌کشی، جفت‌سازی، کشف، مانیتور همتا، هندلرهای سمت سرور
  sync/      برنامه‌ریز (۸ وضعیت) + موتور اجرا (نشست‌ها، تعارض‌ها)
  transfer/  صف، اجراگر قطعه‌ای، pause/resume، توکن‌باکت
  indexer/   اسکن + هش + fsnotify، اعتبارسنجی مسیر
  netproto/  پروتکل سیمی فریم‌بندی‌شده، TLS 1.3 + pin کردن Ed25519
  identity/  events/ config/ store/ version/
  native/    مدیریت پروسهٔ موتور C++ (JSON-lines)
        │
        ▼
SQLite (meshsync.db) + پوشه‌های اشتراکی + trash/ + parts/
        │
        ▼
شبکهٔ همتا: TLS 1.3 روی TCP (4040)؛ کشف UDP 239.255.42.42:4100
```

## نقشهٔ پکیج‌ها (`agent/internal/`)

| پکیج | مسئولیت |
|---|---|
| `cmd/meshsync-agent` | پارس پرچم‌ها، ترتیب راه‌اندازی، `main.go` |
| `config` | `config.json` + env + پرچم‌ها؛ اعتبارسنجی و اعمال زنده |
| `identity` | هویت Ed25519 ماندگار؛ peerId = ۱۶ نویسهٔ hex اول SHA-256(pubkey) |
| `netproto` | پروتکل سیمی: فریم با طول ۴ بایتی، ۲۳ نوع پیام، تنظیمات TLS، حلقه‌های dial/serve |
| `store` | لایهٔ دسترسی SQLite + اسکیمای `migrations/001_init.sql`، نگاشت قطعه‌ها |
| `indexer` | پیمایش دایرکتوری، تخصیص هش، watch با fsnotify، اعتبارسنجی مسیر (`SafeJoin`) |
| `sync` | محاسبهٔ برنامه (`planner.go`) و اجرای آن (`engine.go`): نشست، تعارض، سطل زباله |
| `transfer` | صف انتقال + استخر worker (`manager.go`)، توکن‌باکت سراسری (`bandwidth.go`) |
| `events` | باس رویداد: ذخیره، fan-out، emitهای throttleشده |
| `native` | چرخهٔ حیات پروسهٔ C++؛ fallback هشِ Go |
| `api` | mux HTTP، میان‌افزار (CORS/توکن/rate limit)، WS |
| `app` | ریشهٔ ترکیب؛ پیاده‌سازی هندلرهای پروتکل سمت همتا |

سایر کامپوننت‌ها: `native/cpp` (موتور هش C++20)، `src/` (کنسول وب)،
`flutter/` (کلاینت)، `docs/`، `deploy/` (Docker)،
`scripts/` (ابزار انتشار).

## اسکیمای دیتابیس (`001_init.sql`)

- `peers` — شناسه، نام، آدرس، کلید عمومی pinشده، وضعیت اعتماد، نسخه/پلتفرم.
- `folders` — نام یکتا + مسیر مطلق هر پوشهٔ اشتراکی.
- `files` — به‌ازای (folder, rel_path): اندازه، mtime، هش،
  `last_synced_hash` و tombstone با `deleted`. ایندکس روی folder و
  tombstoneها.
- `transfers` — جهت، اندازه‌ها، `file_hash`، اندازهٔ قطعه،
  `chunks_total`، نگاشت قطعه‌ها (`chunks_done`)، وضعیت، خطا، نشست.
- `conflicts` — هش/اندازه/mtime هر دو نسخه، همتای ریموت، وضعیت، راه‌حل.
- `events` — لاگ رویداد append-only (شناسه‌ها برای `sinceEventId`).
- `sessions` — رکورد نشست‌های همگام‌سازی (وضعیت، بایت، تعداد فایل، خطا).
- `remote_manifests` — آخرین وضعیت دیده‌شدهٔ هر همتا به‌تفکیک پوشه/مسیر.
- `meta` — فرادادهٔ اسکیما.

SQLite از `modernc.org/sqlite` می‌آید — Go خالص، بدون cgo — تا کامپایل
متقاطع ایجنت بی‌دردسر باشد. زمان‌ها در لایهٔ ذخیره‌سازی unix seconds
(UTC) و در لایهٔ API به قالب RFC 3339 هستند.

## جریان‌های داده

### کشف و جفت‌سازی

۱) هر ایجنت هر ۵ ثانیه بیکِن JSON (`peerId`, `name`, `version`,
`peerPort`) به `239.255.42.42:4100` می‌فرستد؛ لیسنر با `SO_REUSEADDR`
به گروه join می‌کند تا چند ایجنت روی یک هاست هم‌زیستی کنند.
۲) بیکِن‌های ناشناس به‌عنوان همتای `DISCOVERED` ثبت می‌شوند
(+رویداد `PEER_DISCOVERED`).
۳) جفت‌سازی: `POST /peers/pair` به همتای مقصد dial می‌زند، کلید
Ed25519 آن را از گواهی می‌آموزد، `PAIR_REQUEST` می‌فرستد؛ سمت مقابل
رکورد `PAIRING` می‌سازد و رویداد `PAIR_REQUESTED` می‌دهد. تأیید، وضعیت
را `TRUSTED` می‌کند و `PAIR_APPROVED` برمی‌گرداند تا رکورد فرستنده هم
`TRUSTED` شود. نمودار حالت‌ها:
[peer-lifecycle.svg](../assets/peer-lifecycle.svg).

### نمایه‌سازی

- اسکن کامل، پوشه را می‌پیماید (دایرکتوری‌های `.meshsync` نادیده گرفته
  می‌شوند)؛ هر فایل هش می‌شود مگر آنکه (اندازه، mtime) داخل پنجرهٔ
  ۱۵۰۰ میلی‌ثانیه ثابت مانده باشد — mtime فقط میان‌بُرِ اسکنِ محلی
  است؛ تصمیم‌های همگام‌سازی همیشه با هش گرفته می‌شوند.
- fsnotify به‌صورت بازگشتی همهٔ دایرکتوری‌ها را می‌پاید؛ رویدادها با
  debounce ۴۰۰ میلی‌ثانیه (+۵۰ میلی‌ثانیه settle) دوباره نمایه می‌شوند؛
  فایل غایب tombstone می‌شود.
- مسیریابی هش: فایل‌های ≥ ۱ MiB وقتی worker در دسترس است به موتور C++
  می‌روند؛ وگرنه SHA-256 استریمی با بافر ۱ MiB در خود Go. خرابی worker
  یک رویداد `NATIVE_FALLBACK` می‌دهد و ایجنت در حالت Go ادامه می‌دهد.

### نشست همگام‌سازی

۱) `POST /sync/run` (یا `GET /sync/plan` برای اجرای خشک): rescan،
اتصال، ردوبدل مانیفست `INDEX` در هر دو جهت، کش مانیفست ریموت.
۲) برنامه‌ریز اجتماع مسیرهای دو طرف را دسته‌بندی می‌کند (جدول هشت
وضعیت در [SYNC_FA.md](SYNC_FA.md)).
۳) اقدامات کنترلی روی همان اتصال: `CONFLICT_NOTIFY` (باز شدن تعارض در
سمت مقابل)، `DELETE_FILE` (گارد هش)، `ADOPT` (ترمیم `last_synced_hash`
منحرف‌شده بدون انتقال مجدد).
۴) اقدامات PUSH/PULL به صف انتقال می‌روند؛ manager تا
`concurrentTransfers` انتقال موازی اجرا می‌کند: هر قطعه verify، فایل
part، verify کامل، رنم اتمیک، به‌روزرسانی نمایه، `ADOPT` + `FILE_END`.
۵) وضعیت نشست (`COMPLETED`/`FAILED`) + رویدادها؛ پیشرفت زنده با فریم‌های
WS `transfer` و رویدادهای `TRANSFER_PROGRESS`. نمودار:
[sync-flow.svg](../assets/sync-flow.svg).

### ازسرگیری انتقال

وضعیت انجامِ قطعه‌ها یک bitmap در SQLite است. `pause` وضعیت را freeze
می‌کند (و ری‌استارت، انتقال‌های ناتمام را در بوت به `PAUSED` می‌برد)؛
`resume`/`retry` از اولین قطعهٔ pending ادامه می‌دهند؛ مسیر فایل part
قطعی است (`sha256(folderID|peerID|relPath)`)، پس آغازگر و گیرندهٔ
منفعل به یک مکان می‌رسند — همین چیزی است که انتقال را ازسرگیری‌پذیر
می‌کند. نمودار: [chunk-transfer.svg](../assets/chunk-transfer.svg).

## تصمیم‌های طراحی

- **SQLite با Go خالص (`modernc.org/sqlite`).** بدون cgo در ایجنت؛
  کامپایل متقاطع ساده و بدون وابستگی به کتابخانهٔ سیستمی. کار
  پرفورمنسی C++ به‌جای دیتابیس، در موتور هش ایزوله شده است.
- **موتور C++20 با JSON-lines.** هش‌کردن فایل‌های بزرگ، hot path
  CPU-bound است. Worker یک پروسهٔ فرزند است که هر خط یک شیء JSON روی
  stdin/stdout است (`{"op":"hash","path":…}` → `{"ok":true,"hash":…}`)؛
  stderr drain می‌شود و fallback سخت به هش Go وجود دارد. ایجنت بدون آن
  کاملاً کار می‌کند — worker بهینه‌سازی است، نه وابستگی.
- **fsnotify.** ویرایش‌های بیرون از MeshSync در حین اجرا دیده می‌شوند؛
  rescan دوره‌ای/دستی پنجرهٔ آفلاین را می‌پوشاند. debounce، الگوی
  نوشتنِ ادیتورها را جذب می‌کند.
- **gorilla/websocket برای رویدادها.** یک اتصال به‌ازای کلاینت، فریم
  `hello` با اسنپ‌شات دستگاه، fan-out با کانال‌های بافرشده (کلاینت کند،
  فریم را از دست می‌دهد ولی ایجنت بلاک نمی‌شود)، `ping`/`pong`.
- **سطل زباله قبل از عملیات مخرب.** حذف محلی/ریموت و بازنویسی تعارض،
  نسخهٔ بازنده را اول به `~/.meshsync/trash/<folder>/` می‌برند. از دست
  رفتن داده دو قدم صریح لازم دارد.
- **توکن‌باکت پهنای باند.** یک باکت سراسری بین همهٔ انتقال‌ها، به
  تفکیک قطعه در هر دو جهت send/receive؛ burst معادل یک ثانیهٔ نرخ (سقف
  ۸ MiB). قابل پیش‌بینی، بدون ماشین‌آری per-connection.
- **ترجیح هش بر زمان.** میان‌بُرهای mtime/size هرگز نتیجهٔ همگام‌سازی
  بین دو دستگاه را تعیین نمی‌کنند؛ فقط برابری محتوای SHA-256. هزینه‌اش
  هش‌کردن است، اما باگ کلاسیک «اختلاف ساعت، فایل من را له کرد» را
  حذف می‌کند.
- **اجرا برنامه‌اول.** `GET /sync/plan` دقیقاً همان مسیر کدِ
  `POST /sync/run` است منهای نوشتن‌ها؛ پس چیزی که بازبینی می‌کنید همان
  چیزی است که اجرا می‌شود.

## مدل همزمانی

- هر اتصال همتا یک جفت گوروتین است (حلقهٔ خواندن سمت سرور؛ dialer،
  خواندن‌های خودش را مالک است). نوشتن فریم‌ها با mutex در هر اتصال
  سریال می‌شود.
- manager انتقال، یک tick دیسپچ (۲۵۰ میلی‌ثانیه) و یک گوروتین به‌ازای
  انتقال فعال دارد (محدود به `concurrentTransfers`). پرچم‌های کنترل
  (pause/cancel) بین قطعه‌ها چک می‌شوند، نه وسط فریم.
- نمایه‌گر، re-indexهای ناشی از watch را پشت نقشهٔ debounce سریال
  می‌کند؛ حلقهٔ fsnotify تک‌گوروتینه است.
- باس رویداد non-blocking است: مشترک‌ها کانال بافرشده (۲۵۶) دارند؛
  سرریز فقط برای همان مشترک فریم drop می‌کند.
- وضعیت اشتراکی یا با mutex محافظت می‌شود (`peersMu`، `Manager.mu`،
  `Bandwidth.mu`، `cfgMu`) یا atomic است (`stopped`، `skipDot`). تنظیمات
  زنده، یک کپیِ RWMutexدار است — تغییر تنظیمات بدون ری‌استارت اعمال
  می‌شود.

## اتصال مجدد و backoff

- **مانیتور همتا:** هر ۲ ثانیه، همتاهای `TRUSTED`/`PAIRING` با یک dial
  واقعی + HELLO + رفت‌وبرگشت ping پروب می‌شوند (تایم‌اوت ۵ ثانیه).
  شکست‌ها به‌صورت خطی backoff می‌گیرند: ۱۰ ثانیه، ۲۰ ثانیه، … تا سقف
  ۶۰ ثانیه. تغییر وضعیت، رویداد `PEER_ONLINE`/`PEER_OFFLINE` و فریم WS
  `peers` می‌فرستد.
- **کلاینت‌ها:** در پروتکل WS قطع‌شدن طبیعی اعلام شده؛ کلاینت‌ها با
  backoff وصل می‌شوند (کنسول وب: ۱ ثانیه تا سقف ۳۰ ثانیه) و بعد از
  هر (re)connect کل وضعیت را از REST می‌گیرند. وضعیت کهنهٔ WS هرگز
  مرجع نیست.
- **ری‌استارت ایجنت:** انتقال‌های ناتمام `PAUSED` می‌شوند (bitmap
  ماندگار)، پوشه‌ها rescan و دوباره watch می‌شوند، کشف بیکِن‌ها را از
  سر می‌گیرد. جفت‌سازی مجدد لازم نیست — هویت و اعتماد ماندگارند.
